# OrderFlow — CI Audit Lab · Advanced

Учебный сервис управления заказами с каталогом, скидками, резервированием остатков,
расчётами с поставщиками, правами доступа, платежами, уведомлениями, импортом и отчётами.

**Назначение:** комплексный аудит исходного кода через GitHub Actions, Ruff, Semgrep
и самостоятельные проверки бизнес-инвариантов. Проект содержит намеренно внесённые дефекты.
Не размещайте приложение в интернете и не используйте для реальных платежей.

## Быстрый запуск

```bash
python -m pip install pytest ruff semgrep
python -m pytest -q
ruff check src
semgrep scan --config rules/orderflow.yml --error --metrics=off src
```

Для веб-интерфейса (локально):

```bash
python -m pip install -e .
python -m orderflow.web
```

Проверка доступности: http://127.0.0.1:8765/health

### GitHub Actions

Файл `.github/workflows/ci.yml` содержит три независимых job: Unit tests,
Ruff quality gate и Semgrep security gate. Для начала практики ожидается,
что unit-тесты проходят, а часть анализаторов сообщает о нарушениях.

1. Создайте Fork учебного репозитория.
2. На вкладке Actions при необходимости разрешите выполнение workflow.
3. Создайте ветку `student/audit-<ваш-идентификатор>`.
4. Исследуйте найденные предупреждения; подтвердите важные из них кодом и тестами.
5. Исправьте причины, а не отключайте проверки.
6. Отправьте изменения в свой Fork и создайте Pull Request.

**Правила работы:** не редактируйте `rules/orderflow.yml` и workflow ради
«зелёной галочки»; не удаляйте тесты и проверяемые модули. Не все дефекты
выявляются стандартными правилами — исследуйте граничные случаи.

### Подсказка без ответов

Проверьте атомарность резервирования, возвраты сумм при округлении,
разграничение прав организаций, проверку адресов внешних сервисов,
повторные коды скидок, импорт табличных данных и сопоставление платежей.

### 1. Аудит текущего CI и определение требований

**1.1** Ветка `audit/mikhailov` создана от `main`. Изучены `.github/workflows/ci.yml`
(три job: `tests`, `quality`, `security`), `pyproject.toml` (Ruff: `select=[E4,E7,E9,F,B,SIM]`,
`ignore=[E501]`; pytest: `testpaths=tests`, `pythonpath=src`) и `rules/orderflow.yml`
(9 синтаксических Semgrep-правил, по одному на каждый ранее заложенный класс дефекта).

**1.2** Разбор по каждому job: команда, область, критерий успеха, причины ложного/неполного
результата.

- **`tests` (Unit tests)** — команда `python -m pytest -q`; область — поведение функций,
  покрытых существующими test-кейсами; критерий успеха — код возврата 0 (все `assert`
  истинны). Причины ложного/неполного результата: тест не описывает нужный сценарий (пробел
  в спецификации, а не сбой инструмента); использование реального времени в функциях вроде
  `session_valid`/`reservation_expired` без фиксации `now` может сделать тест нестабильным
  (flaky); ошибка установки pytest из PyPI даёт красный статус, не связанный с кодом.
- **`quality` (Ruff quality gate)** — команда `ruff check src`; область — синтаксические и
  стилистические паттерны из выбранного набора правил (`E4`/`E7`/`E9`/`F`/`B`/`SIM`) по всему
  `src/`; критерий успеха — 0 нарушений. Причины ложного/неполного результата: набор правил
  узкий и не включает проверки безопасности (линтер не предназначен искать SQL-инъекции или
  ошибки бизнес-логики вроде неатомарного резервирования — они вне его области по
  конструкции); срабатывание само по себе не означает поломку поведения (например, `F401`
  «неиспользуемый импорт» никогда не влияет на результат вычислений); нефиксированная
  минорная версия (`ruff>=0.9,<1`) может менять набор срабатываний между запусками.
- **`security` (Semgrep security gate)** — команда
  `semgrep scan --config rules/orderflow.yml --error --metrics=off src`; область — 9
  собственных синтаксических паттернов, каждый ищет конкретную форму кода (обход
  tenant-границы, mass assignment, сравнение через `endswith` и т.д.); критерий успеха — 0
  совпадений (`--error` делает любое совпадение кодом выхода ≠0). Причины ложного/неполного
  результата: правило ловит только ту форму кода, под которую написано — наглядно показано
  в п. 2.3 (false negative на реальной SQL-инъекции); даже реальное совпадение требует
  человеческой проверки достижимости и контекста — это *Finding*, а не доказанная
  уязвимость.

  **Вывод:** ни Ruff, ни Semgrep не исполняют код — это статический анализ текста/AST.
  Только `tests` реально наблюдает поведение программы, и то лишь в границах того, что
  авторы тестов додумались проверить.

**1.3** Выбраны 4 требования к качеству (два автоматизируемых уже сейчас, одно про
бизнес-логику, одно про надёжность CI):

| Требование | Свидетельство / инструмент | Критерий PASS | Область проверки |
|---|---|---|---|
| Нет неиспользуемых импортов и небезопасных замыканий в цикле (`F401`, `B023`) | Ruff (`ruff check src`) | `ruff check src` завершается кодом 0 | весь `src/` — автоматизируемо уже сейчас |
| Сравнение API-ключа и подписи вебхука защищено от timing-атак | Semgrep-правило `orderflow-audit-key-comparison` + unit-тесты `verify_api_key`/`verify_webhook` | 0 блокирующих находок Semgrep и тесты проходят | `accounts.py` — автоматизируемо уже сейчас |
| Резервирование товара атомарно: неудачная попытка не меняет остаток склада | Регрессионные тесты `tests/test_reservation_invariants.py` (факт до/после) | `stock` после `False` равен `stock` до вызова `reserve_items` | `fulfillment.reserve_items`, `inventory.allocate_order` — бизнес-логика, не покрывается Ruff/Semgrep |
| CI сохраняет машиночитаемую историю прогона тестов, доступную даже при падении job | `actions/upload-artifact` (JUnit) в job `tests` + проверка наличия артефакта после запуска Actions | артефакт `pytest-junit-report` присутствует независимо от исхода job | `.github/workflows/ci.yml`, job `tests` — надёжность/диагностируемость CI |

Последствие нарушения для каждого (отдельная колонка в таблицу не влезала по формату
задания, поэтому указываю здесь):

1. **Импорты/замыкания** — не ломает поведение немедленно, но копит мёртвый код и ошибки
   позднего связывания в циклах, которые проявятся, когда кто-то начнёт вызывать колбэк
   отложенно (как в `notify_followers`).
2. **Timing-safe сравнение** — побайтовое сравнение через `==` открывает атаку по времени
   отклика (timing attack), позволяющую подобрать ключ/подпись и обойти аутентификацию
   вебхука или API.
3. **Атомарность резервирования** — расхождение между фактическим остатком склада и книгой
   подтверждённых заказов: товар списывается, но ни один заказ его не получает; расхождение
   не видно до ручной инвентаризации.
4. **JUnit-отчёт в CI** — без него причина падения job видна только в сыром консольном
   логе, что удлиняет диагностику и подталкивает к практике «перезапустить job, не
   разбираясь» (см. flaky tests, раздел 1.6 теории).

### 2. Инженерная диагностика результатов

**2.1** Диагностика взята на состоянии до аудита (`main`), job **«Ruff quality gate»**,
шаг `ruff check src`:

job → step → команда → причина:
«Ruff quality gate» → «Run ruff check src» → `ruff check src` → 3 нарушения:
`F401` неиспользуемый импорт `.shipping.delivery_estimate` в `fulfillment.py:4`;
`F401` неиспользуемый импорт `datetime.timezone` в `inventory.py:3`;
`B023` — замыкание в `notifications.py:27` не связывает переменную цикла `follower` по
значению (позднее связывание).

Это настоящие нарушения кода, а не сбой самого инструмента: Ruff завершился штатно (код
возврата 1 означает «найдены нарушения», а не крах анализатора), каждое сообщение указывает
точную строку и воспроизводимое условие. Все три устранены коммитами `6bfbb38` и `00b6960`
в истории ветки; статус job после исправления — PASS.

**2.2** Две находки разных категорий (на состоянии `main`, до исправления):

- **Semgrep, `orderflow-authorization-tenant-boundary`, `access.py`:**
  ```python
  if principal.role == 'admin':
      return True
  ```
  Риск: проверка роли `admin` возвращала `True` безусловно, раньше проверки совпадения
  `tenant_id` — то есть администратор любой организации мог просматривать заказы любой
  другой организации. Подтверждение: `can_view_order` — единственная точка авторизации для
  `visible_orders`, и `tenant_id` — единственная граница изоляции организаций в этой функции.
  Способ исправления, не ломающий нужную функциональность: сначала жёстко проверять
  принадлежность к tenant, и только внутри своей организации разрешать `admin` расширенный
  доступ — именно так и исправлено (`same_tenant` проверяется первым;
  `role == 'admin' or owner_id == user_id` работает только после прохождения этой проверки).

- **Ruff, `F401`, `fulfillment.py:4`:** `from .shipping import delivery_estimate`.
  Риск: нулевой для поведения — чисто сигнал мёртвого кода. Подтверждение: `delivery_estimate`
  нигде в `fulfillment.py` не используется. Исправление: импорт удалён (коммит `6bfbb38`),
  функциональность не затронута.

**2.3** `B023` в `notifications.py` — истинное срабатывание с реально небольшим радиусом
действия: единственный вызывающий код использует каждый колбэк немедленно до следующей
итерации, поэтому дефект не проявлялся на практике — тем не менее исправление оправдано:
любой будущий вызывающий код, сохраняющий колбэки для отложенного вызова, получит у всех
записей одно и то же (последнее) значение `follower`.

Более показателен обратный случай — не False Positive, а **False Negative**: правило
`orderflow-query-composition` специально написано для этого проекта, чтобы ловить
динамическую сборку SQL через f-строку, но ни разу не сработало на реальную SQL-инъекцию в
`storage.py: find_orders_by_email` (проверено `semgrep scan` по одному этому файлу — 0
находок и до, и после ручного исправления). Зелёный security-gate в этом репозитории никогда
не означал «SQL-инъекций нет» — он означал лишь «нет кода, синтаксически совпадающего с
`$Q = f"SELECT ..."` в точке присваивания». Отсутствие находок — это не доказанная
безопасность, а лишь то, что было проверено данным набором правил.

### 3. Самостоятельный поиск и регрессионная проверка

**3.1** Выбрана операция «резервирование товара» (`fulfillment.reserve_items`, в паре со
вторым, уже корректным образцом той же операции — `inventory.allocate_order`). Инварианты:
(1) остаток склада не может стать отрицательным; (2) резервирование корзины — атомарная
операция «всё или ничего»: либо удовлетворены все строки корзины и остаток уменьшен ровно на
запрошенные количества, либо остаток не меняется вовсе; (3) неположительное количество
должно быть отклонено до каких-либо изменений состояния.

**3.2** Добавлены два новых сценария в `tests/test_reservation_invariants.py` (их не было в
исходном наборе):

1. **Граничный:** корзина из одной строки запрашивает ровно весь доступный остаток
   (`test_reserve_exact_available_stock_boundary`) — граница между успехом (`==`) и отказом
   (`>`).
2. **С повторной операцией/несколькими объектами:** корзина с двумя строками на один и тот
   же SKU, суммарное количество которых превышает остаток
   (`test_reserve_rolls_back_when_a_later_line_cannot_be_satisfied`) — проверяет атомарность
   резервирования корзины целиком.

Факт до изменения реализации (зафиксирован прогоном pytest до правки `fulfillment.py`):
сценарий 1 — PASS; сценарий 2 — **FAIL**
(`AssertionError`: `stock` стал `{'SKU-1': 2}` вместо ожидаемого отката к `{'SKU-1': 5}`).

| Обнаруженная проблема / сценарий | Метод проверки | Факт до изменения | Факт после изменения | Вывод |
|---|---|---|---|---|
| Резервирование: корзина с двумя строками на один SKU суммарно превышает остаток | pytest (`test_reserve_rolls_back_when_a_later_line_cannot_be_satisfied`) | `stock {'SKU-1': 5} → {'SKU-1': 2}`, функция вернула `False` (частичное списание без отката) | `stock` остаётся `{'SKU-1': 5}`, функция возвращает `False` | Дефект подтверждён и исправлен (two-pass: проверка всех строк, затем единое списание) |
| Резервирование: граничный случай — запрошено ровно всё доступное количество | pytest (`test_reserve_exact_available_stock_boundary`) | `True`, `stock → 0` (уже работало) | без изменений: `True`, `stock → 0` | Дефекта не выявил; тест фиксирует границу как регрессионный контракт |
| SQL-инъекция в поиске заказов по email (`storage.find_orders_by_email`) | Ручной PoC (payload `x' OR '1'='1'`) + pytest-регрессия `test_storage_rejects_sql_injection_payload` | payload возвращал все заказы в базе (обе тестовые записи) | возвращает пустой список `[]` | Дефект подтверждён и исправлен (параметризованный запрос); Semgrep не ловит — False Negative |

**3.3** Сценарий 2 выявил дефект. Первопричина: `reserve_items` изменял `stock` построчно и
возвращал `False` сразу при первой неудовлетворимой строке, не откатывая уже применённые
списания и не вызывая компенсирующий `release` — часть товара «терялась» в остатке без
какого-либо подтверждённого резервирования. Исправление: функция переписана в два прохода —
сначала агрегируется требуемое количество по каждому SKU и целиком проверяется против
исходного остатка, и только после успешной проверки всех строк происходит фактическое
списание; тот же паттерн, что уже корректно применён в `inventory.allocate_order`. После
исправления оба новых теста проходят, а весь исходный набор по-прежнему проходит без
регрессий (итого 26 тестов). Заодно по собственной инициативе исправлена обнаруженная при
изучении соседнего модуля `storage.py` SQL-инъекция в `find_orders_by_email` (f-строка
заменена на параметризованный запрос), добавлен регрессионный тест с payload
`x' OR '1'='1'`.

### 4. Развитие политики CI

**4.1** Выбран вариант: формирование и сохранение JUnit-отчёта pytest
(`--junitxml=reports/pytest.xml`) как артефакта job `tests`
(`actions/upload-artifact@v4`, `retention-days: 14`).

**4.2** Какой риск/наблюдение улучшает: красный статус «Unit tests» давал только
необработанный лог в консоли Actions — чтобы понять, какой именно `assert` упал и где, нужно
было вручную искать по логу. JUnit XML даёт структурированную, пригодную для парсинга и
сохранённую запись результата каждого теста с таймингом, доступную даже позже, отдельно от
журнала запуска. Когда выполняется: при каждом запуске job `tests`, то есть на тех же
событиях `push`/`pull_request`, что и раньше — новый job не добавлен, расширен существующий.
Блокирующий ли: да — шаг pytest выполняется с `continue-on-error: true` только для того,
чтобы отчёт успел загрузиться как артефакт даже при падении тестов, но следующий шаг
немедленно возвращает ошибку (`exit 1`), если был провал — итоговый статус job не ослаблен.
Как определять причину падения: скачать артефакт `pytest-junit-report` со страницы запуска
Actions и открыть XML — там указаны все упавшие `testcase` с сообщением `assert`, без
необходимости листать полный лог.

**4.3** Новых прав не запрошено: `permissions: contents: read` в начале файла не менялся.
`actions/upload-artifact@v4` работает на встроенном `GITHUB_TOKEN` и не управляется блоком
`permissions` (это не Checks/Issues/Contents API) — дополнительных scope не требуется. Job не
читает и не пробрасывает секреты, поэтому утечка токенов через артефакт исключена по
конструкции (в отчёт попадают только имена тестов, время выполнения и текст `assert`).

### 5. Проверка изменений через Pull Request

**5.1** Изменения закоммичены в ветку `audit/mikhailov`. Проверки запускаются по событию
`pull_request` (`branches: [main]`) сразу при открытии PR в основную ветку форка. При
диагностике обнаружено, что событие `push` изначально фильтровалось по
`branches: [main, "student/**"]` — ветки вида `audit/<фамилия>`, которые сама же практическая
часть (п. 1.1) предписывает создавать, под этот фильтр не попадали, и `push` в них не
запускал Actions вовсе (только открытие PR против `main`). Это реальный пробел конфигурации
триггеров, а не ожидаемое поведение: workflow не поспевал за собственным соглашением об
именовании ветки. Исправлено добавлением `"audit/**"` в список `branches` для `push`, так что
CI теперь запускается автоматически уже на `git push` в ветку аудита, не дожидаясь открытия
PR.

**5.2** Краткое заключение:

- **Исправлено:** (1) неатомарность резервирования в `fulfillment.reserve_items` — добавлены
  2 регрессионных теста и two-pass реализация по аналогии с `inventory.allocate_order`;
  (2) SQL-инъекция в `orderflow.storage.find_orders_by_email` — запрос параметризован,
  добавлен регрессионный тест; найдена вручную, так как правило Semgrep
  `orderflow-query-composition`, написанное именно под этот класс дефекта, на неё не
  сработало (False Negative, см. п. 2.3).
- **Подтверждено, но оставлено на дальнейшую работу:**
  (a) повторная подача одного и того же кода скидки в `apply_promotions` не игнорируется, а
  суммируется — `apply_promotions(4000, ['OFFICE7','OFFICE7'], ['office'])` даёт `3460`
  вместо `3720` за единственное применение (соответствует подсказке задания «повторные коды
  скидок»); решение, нужно ли это запрещать или это осознанное поведение multi-stack-скидок —
  продуктовый вопрос, выходящий за рамки одной инженерной правки, поэтому оставлен как
  задокументированный риск, а не исправлен в этом PR;
  (b) структуры `Warehouse`/`stock` не имеют блокировок, а `web.py` поднимает
  `ThreadingHTTPServer` — при реальном параллельном трафике два потока могут одновременно
  пройти проверку доступности и перепродать один и тот же товар (race condition). Ни Ruff,
  ни Semgrep, ни однопоточные unit-тесты такое в принципе не обнаружат.
- **Можно ли мёрджить при текущих результатах:** да — все три job (`tests`, `quality`,
  `security`) проходят, добавлены регрессионные тесты на найденный и исправленный дефект, ни
  одна проверка не отключена и не ослаблена ради «зелёной галочки». Риск, который этот CI
  всё ещё не контролирует: пункт (b) выше — конкурентная гонка при резервировании склада под
  реальной многопоточной нагрузкой.
